# Milestone roadmap

Read [product baseline](product-plan.md), [handoff](manager-handoff.md), [workflow](development-workflow.md). Inspect [issue #3](https://github.com/shivdevwalia/yorku_app/issues/3) and its linked PR for current documentation review/merge status; baseline approval alone authorizes no execution or extra milestone issues. No delivery date until data feasibility; later estimates require measured scope/evidence.

## 0 — Source and rights feasibility

**Dependencies:** Explicit execution authorization; inspect baseline/repository/open work first.

**Scope:** Source/rights inventory separating access from redistribution/retention/display/third-party rights; representative catalog/rules/offerings audit including connected subjects, calendars, compatibility, dates/campus, ambiguity, refresh feasibility. Choose pilot from evidence; EECS/MATH are candidates only.

**Acceptance:** Evidence-backed rights/source matrix, unresolved decisions, representative coverage assessment, measurable pilot criteria, proposed freshness/unknown policy, go/no-go recommendation. No verified feed/parser claim.

**Exit:** User reviews feasibility and approves next scope. Missing critical data/unresolved rights block affected features; reduce/defer rather than fabricate. Execution pending authorization.

## 1 — Foundation, pipeline, explorer

**Dependencies:** Milestone-0 exit, approved pilot/rights boundaries, explicit execution approval.

**Scope:** Validate proposed Python stack, modular monolith/worker, PostgreSQL schema, permitted object storage, Next.js/TypeScript shell, OpenAPI contracts, pipeline, explorer, CI. Contracts precede independent data and UI/domain work.

**Acceptance:** Explorer exposes pilot fields/relationships/offerings with provenance/freshness/coverage. Fixture pipeline detects failures/mass loss, quarantines invalid data, preserves unknowns, supports reviewed publication/rollback. Actual frontend type/lint/build, Python lint/type/domain, ingestion regression, contract compatibility, integration checks have evidence. Phone/keyboard and text requirement view work.

**Exit:** Exact-SHA review, reproducible publication/explorer evidence, no unsupported claims. Stable required checks only after reliable checks exist. Explicit merge/deployment approval.

## 2 — Useful next-term MVP

**Dependencies:** Milestone-1 validated data/pipeline/contracts, approved scope, agreed rule/schedule semantics before parallel work.

**Scope:** Manual history, three-valued requirements, AND/OR search, valid bundles, date/travel conflicts, blocked time, pins, deterministic ranking, saved plans/versions/revalidation, export, official links, corrections. Public exploration remains; accounts require privacy/access-control evidence.

**Acceptance:** Students complete useful tasks on phone/keyboard. Fixtures cover AND/OR/grade/permission/unknown, corequisites/exclusions/crosslistings, compatibility, dates/campus/travel/async versus unknown, pins/blocked time, scoring ties, limits, no-solution explanations. Plans reproduce from recorded versions and visibly revalidate; exports match dated meetings. Unsupported evidence never appears verified.

**Exit:** Reviewed MVP evidence/limits; no Passport York/enrolment/chatbot/paid LLM dependencies or false optimality. Explicit merge/deployment and release-audience approval.

## 3 — Coverage expansion

**Dependencies:** Milestone-2 gates plus source/rights/coverage validation per expansion.

**Scope:** Expand subjects/faculties through shared model/rule engine and validated adapters. Unsupported professional/graduate cases remain disabled.

**Acceptance:** Each area has provenance, rights decisions, representative fixtures, rule/meeting validation, freshness policy, student usability evidence. Regression protects pilot; unknown/correction workflows remain visible.

**Exit:** Accurate enabled/unsupported coverage matrix, independent review, explicit release approval. All-faculty design is not complete live coverage.

## 4 — One validated program/calendar degree planner

**Dependencies:** Milestone-3 exit; selected program/calendar rules/rights validated with qualified review process.

**Scope:** One reviewed roadmap/degree interpretation: credit counting, alternatives, exclusions, historical rules, unresolved equivalences. Not every program.

**Acceptance:** Reviewed representative histories/graduation what-if cases yield traceable explanations, unknowns, assumptions. Validate crosslisting/equivalence/double counting. Distinguish estimates from official Degree Progress Report/graduation decisions.

**Exit:** Record program/calendar coverage/review owner; unsupported cases unknown/disabled. Exact-SHA review and explicit merge/deployment approval.

## 5 — Social and advanced

**Dependencies:** Milestone-4 exit, separate feature approvals, privacy/consent review, rights validation.

**Scope:** Optional licensed ratings, opt-in friends/freebusy, group optimization, broader reviewed roadmaps, advanced graduation what-if. Evaluate OR-Tools only for measured complexity. Ratings never a dependency.

**Acceptance:** Sharing consented, minimized, access-controlled, revocable, tested. Group search exposes hard/soft rules and limits; ratings have verified licensing/display rights. Results deterministic, versioned, explainable, honest about unknowns/optimality.

**Exit:** Feature-specific independent review and explicit merge/deployment approval; defer unsafe/unlicensed/unvalidated features.

## Coordination

One manager per milestone owns dependencies/integration/handoff. Max two independent implementers; data and UI/domain split only after contracts, overlap/dependencies serialized. Track issue/PR links, T3 task/thread IDs, exact bases/heads. Completion events, never polling. New exact-SHA reviewer each round. Checks/draft PRs never authorize merge/deployment. No extra milestone issues in this documentation task.
